# CLAUDE.md - Server

This file provides guidance for working with the AI Together server (backend API).

## Module Overview

The server is a Go backend that provides centralized management, authentication, and usage tracking for the AI Together platform. It handles team management, provider configuration, and aggregates usage data from member clients.

**Module name:** `switch-server`
**Module path:** `server/`

```bash

```

## Server-Specific Architecture

### Dependency Wiring in server.go

All dependencies are manually wired in `server.go` in this order:
1. Load configuration
2. Run database migrations
3. Initialize database connection pool (`pgxpool`)
4. Initialize repositories → services → handlers
5. Register routes with Gin router

**Key initialization:**
```go
// Repositories require database
userRepo := repository.NewUserRepository(database)

// Services require repositories
userService := services.NewUserService(userRepo)

// Handlers require services
authHandlers := handlers.NewAuthHandler(userService, teamService)
```

### Multi-Tenant Data Isolation

- All tables have `tenant_id` column
- JWT tokens include tenant context
- All repository queries automatically filter by tenant
- Foreign key relationships enforce tenant data segregation

### Route Groups

- **Public**: `/auth/*`, `/health` - No authentication required
- **Protected**: `/api/v1/*` - Requires JWT via `AuthMiddleware`
- Middleware injects user context into `c.Get("user")`

## API Endpoints (Quick Reference)

### Authentication (`/auth`)
- `POST /register` - User registration
- `POST /login` - Login (returns JWT access + refresh tokens)
- `POST /refresh` - Refresh access token
- `POST /verify` - Token validation

### Teams (`/api/v1/teams`)
- CRUD operations for teams
- Member management: `/teams/:id/members`
- Settings: `/teams/:id/settings`

### Providers (`/api/v1/providers`)
- CRUD operations for AI providers
- Test connectivity: `POST /providers/:id/test`
- Enable/disable: `POST /providers/:id/enable`
- Stats: `/providers/:id/stats`

### Usage (`/api/v1/usage`)
- Current usage: `/usage/current`
- Statistics: `/usage/stats`
- Batch upload: `POST /usage/batch`

### Proxy (`/api/v1/proxy`)
- Forward AI tool requests: `ANY /proxy/:provider/*model`
- Validate: `POST /proxy/validate`

## Database

### Core Tables
- `tenants` - Organizations
- `users` - User accounts (bcrypt passwords)
- `teams`, `team_members` - Team management
- `providers` - AI provider configurations
- `request_log` - Detailed usage tracking
- `team_usage_summary` - Aggregated statistics

### Migrations

- Located in `/migrations` directory
- Run automatically on startup via `db.RunMigrations()`
- Format: `XXXX_name.up.sql` and `XXXX_name.down.sql`

### SQL Queries (sqlc)

- SQL queries defined in `/internal/db/*.sql` files
- Go code generated by [sqlc](https://sqlc.dev/)
- Regenerate with: `make server-sqlc-gen` or `sqlc generate`
- Generated code in `/internal/db/*.go`

**Common sqlc workflow:**
1. Edit SQL query in `server/internal/db/providers.sql`
2. Run `make server-sqlc-gen` to regenerate Go code
3. Update repository/service layers to use new generated types
4. Rebuild and test

### Connection

- Uses `pgxpool` for connection pooling
- Connection string from `DATABASE_URL` environment variable

## Service Layer Patterns

### LicenseService

Handles license validation and limit enforcement. See [LICENSE_SYSTEM.md](LICENSE_SYSTEM.md) for comprehensive documentation.

**Key Methods**:
- `GetEffectiveLicense()` - Get license or default fallback (never returns nil)
- `CanAddUser()` - Check if user can be added (seat limits)
- `CanAddProvider()` - Check if provider can be added (tier limits)

**Enforcement Pattern** - Always check limits before database operations:
```go
// Check user seat limit
if ok, _ := licenseService.CanAddUser(ctx, tenantID); !ok {
    return errors.New("user limit reached")
}

// Check provider limit
if ok, _ := licenseService.CanAddProvider(ctx, tenantID, kind); !ok {
    return errors.New("provider limit reached")
}
```

**License in Handlers** - Access from request context (injected by middleware):
```go
license, _ := c.Get("license")
lic := license.(*models.License)
if lic.MajorTier() == 0 {
    // Tier 0 has 2 providers per kind limit
}
```

## Common Server Tasks

### Add New API Endpoint

1. Add handler method in appropriate `/handlers` file
2. Register route in `server.go` (public or protected group)
3. Add business logic in `/services` if needed
4. Add database operations in `/repository` if needed
5. Create migration if new tables/columns required

### Modify Database Schema

1. Create new migration in `/migrations`
2. Update SQL queries in `/internal/db/*.sql` files
3. Regenerate database code: `make server-sqlc-gen` or `sqlc generate` (from server/ directory)
4. Update repository methods to use new generated code
5. Test both up and down migrations

**Important:** After modifying SQL query files (e.g., `providers.sql`), always run `make server-sqlc-gen` to regenerate the Go database code before rebuilding.

### Repository Pattern Reference

Each repository handles specific entity:
- `UserRepository` - users, tenants
- `TeamRepository` - teams, team_members
- `ProviderRepository` - providers, testing, enable/disable
- `UsageRepository` - usage tracking, statistics
- `LicenseRepository` - license storage and validation

## Architecture Layers

The server follows a clean three-tier architecture:

### Handlers (`server/handlers/`)
- HTTP request handlers
- Extract data from requests
- Call services for business logic
- Return JSON responses

### Services (`server/services/`)
- Business logic layer
- Orchestrate repository calls
- Implement validation and authorization
- Handle transactions

### Repository (`server/repository/`)
- Database access layer
- SQL queries and data operations
- Map database rows to models
- Handle connection management

### Middleware (`server/middleware/`)
- `AuthMiddleware` - JWT validation
- `CORSMiddleware` - CORS handling
- `LoggingMiddleware` - Request logging
- `LicenseMiddleware` - Injects effective license into request context

### Models (`server/models/`)
- Data transfer objects
- Request/response structures
- Domain models

## Common Issues

### Migration errors
```bash
# Check DATABASE_URL in .env
# Ensure PostgreSQL is running
psql -h localhost -U username -d codetogether
```

### Port already in use
```bash
lsof -ti:9080 | xargs kill -9
```

### JWT validation errors
- Check `JWT_SECRET` in `.env` matches between server restarts
- Verify token hasn't expired (default 24 hours)

### Database connection errors
- Verify `DATABASE_URL` format: `postgres://user:pass@host:port/db?sslmode=disable`
- Ensure PostgreSQL is accessible
- Check database exists and user has permissions
